# Module `archive`

Retention, legal hold, destruction and archive packages (business concept 7.4).

Layout: `api` holds public types and interfaces, `core` the implementation. Other modules may only depend on `api`.

## Legal holds (US-08.1, DMS-56, DMS-106, ADR 0031, 0047)

A legal hold suspends the destruction of the documents it covers until it is released explicitly. A hold names the matter (Vorgang) it was set for, with an optional reference such as a case number, and covers any number of documents; a document can be covered by several holds and is under legal hold while at least one active hold covers it. A hold covers the whole document, all versions including later ones.

- `api`: `LegalHold` (id, name, matter reference, reason, creator, release, document count), `HeldDocument` (document, `HoldSource` Document|Search, reason, who, when, `removal` if it was taken out of the hold), `NewLegalHold`, `LegalHoldError`; `LegalHoldLookup` for the destruction proposals and the destruction path (DMS-82): `isUnderLegalHold(document)`, `heldAmong(documents)`, `activeHolds(document)`; `LegalHoldEvents` (outbox events, job kind).
- `core`, `LegalHoldService` (inside `Db.transact(tenant)`): `create(hold, documents, source, actor)`, `addDocuments(id, documents, reason, source, actor)` (skips documents the hold covers already; returns the new ones), `removeDocument(id, document, reason, actor)` (DMS-106: the entry stays as history, the document is no longer covered by the hold), `release(id, reason, actor)`, `get`, `list(active)`, `documents(id)` (including removed entries). Name and reason are required (`Invalid`); a released hold cannot change (`Released`). Audit entries `legal-hold.created`, `legal-hold.documents-added`, `legal-hold.released` on the hold and `legal-hold.document-removed` on the hold and `document.legal-hold-set` / `document.legal-hold-released` / `document.legal-hold-removed` on each document, all with the reason; outbox events `legal-hold.created`, `legal-hold.documents-added`, `legal-hold.document-removed`, `legal-hold.released`; one job `archive.legal-hold-sync` per affected document. `LegalHoldStore` implements `LegalHoldLookup`.
- `core`, `LegalHoldSync`: handler of `archive.legal-hold-sync`. Sets the S3 object legal hold (ADR 0016) on every rendition object version referenced by the document's versions while the document is held, and removes it afterwards. Reads the current state and repeats if it changed meanwhile, so duplicate and reordered jobs are safe. Best effort: a missing object, a store without legal hold support or missing permissions are logged as warnings and skipped; an unreachable store fails the job (retried by the job runner). Registered in `dms.app.Background`.
- Migration V19: `dms.legal_hold` (released once with time, releaser and reason; never deleted; only the release columns are updatable) and `dms.legal_hold_document` (insert-only, only into active holds), both with RLS on `dms.current_tenant()`. `dms.document_under_legal_hold(document)`. Trigger `document_version_legal_hold_guard`: no version of a held document becomes `Destroyed` (locks the document row against a concurrent hold). Trigger `document_version_rendition_legal_hold`: a new rendition of a held document enqueues the synchronization.
- Migration V30 (DMS-106): removal of a single document: `removed_at`, `removed_by`, `removal_reason` on `dms.legal_hold_document`, set once while the hold is active (trigger `legal_hold_document_change_guard`, update grant on these columns only; deletes stay forbidden); surrogate key `entry_id` and a unique index on `(hold_id, document_id)` for rows not removed, so a removed document can be added again. `dms.document_under_legal_hold` ignores removed rows.

### API (`dms.app.LegalHoldApi`)

All endpoints require `ManageRetention` (records manager) for the whole tenant; every document put under a hold also requires `ManageRetention` on the document (scope, confidentiality), otherwise nothing is stored (403).

| Method | Path | Behaviour |
|---|---|---|
| POST | `/api/v1/legal-holds` | `{name, reason, matterReference?, documentIds?, searchFilter?}` → 201 hold with `addedDocumentIds`. 422 without name or reason. |
| GET | `/api/v1/legal-holds?status=active\|released\|all` | Holds, latest first (default active). |
| GET | `/api/v1/legal-holds/{id}` | Hold with its documents (`documentId`, `title` if the caller may manage the document, `addedVia`, `reason`, `addedBy`, `addedAt`). |
| POST | `/api/v1/legal-holds/{id}/documents` | `{reason, documentIds?, searchFilter?}`; documents already covered are skipped. 422 without reason or documents, 409 `released`. |
| POST | `/api/v1/legal-holds/search-preview` | Search filter → `{total, documents: [{documentId, title, documentNumber?, manageable, underLegalHold}], fingerprint}`: the distinct documents of all hits, for review before confirming (DMS-106). |
| POST | `/api/v1/legal-holds/{id}/documents/{documentId}/remove` | `{reason}`; 422 without reason, 404 if the hold does not cover the document, 409 `released`. Needs `ManageRetention` on the document as well. |
| POST | `/api/v1/legal-holds/{id}/release` | `{reason}`; 422 without reason, 409 `released` if released before. |

`searchFilter` = `{q?, class?, status?, lang?, expectedCount, expectedFingerprint?}`: the parameters of `GET /api/v1/search` plus the hit count (`total`) the caller confirms and, optionally, the `fingerprint` of the preview they reviewed (SHA-256 over the sorted document ids). The server re-runs the search as the caller and puts the documents of all hits under the hold; `409 result_changed` if it finds a different number or, with the fingerprint, other documents now, `422 too_many_documents` above 1000 hits. Lists mark held documents for every reader: `legalHold` in `GET /api/v1/documents`, the search hits and the library items (no hold details). The document view (`GET /api/v1/documents/{id}`) shows `legalHold` and, for callers with `ManageRetention` on the document, `legalHolds` (`id`, `name`, `matterReference`, `createdAt`).

Tests: `LegalHoldServiceSpec` (PostgreSQL and SeaweedFS: service, RLS, history guards, destruction guard, object legal hold), `LegalHoldApiSpec` in `app` (HTTP, authorization, reasons, search-result hold with OpenSearch, several holds and release; DMS-106: preview and fingerprint, removal, list markers without hold names).

## Retention, destruction and clean-up (DMS-82, ADR 0054)

Versions whose retention ended are destroyed along a privileged four-eyes path that leaves a tombstone; working states are compacted, the content of discarded drafts is removed after a grace period, and orphaned objects are removed from object storage.

- `api`: `RetentionRule` (key, name, `periodMonths`, `RetentionTrigger` EndOfValidity|Approval|Creation, `fromYearEnd`), `RetentionPeriod` (pure: `endsOn`, `ended`, `triggeredAt`, `KeyPattern`), `DestructionCandidate` / `DestructionList`, `DestructionProposal` with `DestructionItem`s (`ItemOutcome` Pending|Destroyed|Blocked|Rejected, checksums, `DestroyedFile`s), `DestructionRecord` (for evidence reports), `DestructionError` (`SamePerson` for four eyes), `RetentionEvents` (job kinds `archive.object-cleanup`, `archive.maintenance`).
- `core`, `DestructionService` (inside `Db.transact(tenant)`): `rules`, `saveRule` (audited `retention-rule.saved`), `destructionList` (approved versions out of force whose retention ended in the tenant's time zone; versions without rule and with a running retention are counted), `propose(versionIds, reason, actor)` (only listed versions, not under legal hold, not in another open proposal), `approve(id, reason, actor)` / `reject(...)` (four eyes: never the proposer), `get`, `list(status)`, `recordsOf(document)`. Approval re-checks every version (legal hold, retention with the current rule, status) and destroys it in the same transaction: Superseded/Withdrawn → Archived → Destroyed; content becomes `{"format":1,"sections":[]}`, values `{}`, the deviation report empty, the metadata snapshot keeps the system fields (document id and number, class, version, template, rendition checksum, retention rule); working states, attachment links and the original link are deleted, stored files no other version references are deleted. The item records the rendition SHA-256, the approved content SHA-256 (the workflow case's checksum) and the files. Audit `destruction.proposed|approved|rejected` on the proposal, `document.destruction-proposed|destroyed|destruction-blocked|destruction-rejected` on the document; outbox `document.status-changed` (status Destroyed) for the search index.
- `core`, `ObjectCleanup`: job handler of `archive.object-cleanup` (one per released object version after the commit; kept if referenced again or the document is held; Object Lock retention: kept and retried when the retention ends; object legal hold: kept) and `sweep(tenant, dryRun, actor)`: stored files no version links (older than the grace period, not held) are deleted, then every object version under `attachments/`, `renditions/` and `templates/` of the tenant that no row references is removed unless held, locked or younger than the grace period; the run is stored (`dms.storage_cleanup_run`) and audited (`storage.cleanup-run`); `runs(limit)`.
- `core`, `RetentionMaintenance` (`MaintenanceConfig`): job `archive.maintenance` per tenant and interval (default daily), registered in `dms.app.Background`: compaction of working states (`WorkingStateCompaction.removable`: kept are the current state, the latest N (10 open, 1 closed), states saved within 7 days and every state a vote or a deviation request was given on; never under legal hold), removal of the content of drafts discarded longer than 30 days (not under legal hold; audited `document.discarded-content-removed`), and the orphan sweep. Configuration `dms.retention.*` (`application.conf`).
- Migration V35: `dms.retention_rule`, `dms.destruction_proposal` (decided once; check `destruction_proposal_four_eyes`), `dms.destruction_item` (one open proposal per version; outcome set once), `dms.storage_cleanup_run` (insert-only), all with RLS on `dms.current_tenant()` and grants to `dms_app`. `dms.document_version` gets `content_removed_at/by`; its guard allows `Destroyed` only together with the removal of the content and only for a version of an approved proposal decided by another person, and the removal of a discarded draft's content once. Working states may be deleted for destroyed and discarded versions and otherwise only if they are not the current state, not reviewed and not under legal hold. Attachment links and originals may be deleted for destroyed versions.

### API (`dms.app.RetentionApi`)

All endpoints require `ManageRetention` (records manager) for the whole tenant; proposals also need `ManageRetention` on every document, approvals `Destroy` (records manager, second person). The storage clean-up needs `Configure` on the retention area (records managers and tenant administrators).

| Method | Path | Behaviour |
|---|---|---|
| GET | `/api/v1/retention/rules` | Rules by key. |
| PUT | `/api/v1/retention/rules/{key}` | `{name, periodMonths, trigger?, fromYearEnd?}` → rule; 422 for an invalid key, name or period. |
| GET | `/api/v1/retention/destruction-list?class=&rule=&q=` | Candidates (`title` only if manageable, `underLegalHold`, `pendingProposalId`, `manageable`), `withoutRule`, `retentionRunning`. |
| POST | `/api/v1/retention/destruction-proposals` | `{versionIds, reason}` → 201 proposal; 422 without reason or for versions not on the list, 409 held or already proposed. |
| GET | `/api/v1/retention/destruction-proposals?status=proposed\|approved\|rejected\|all` | Proposals, latest first, with `canDecide`. |
| GET | `/api/v1/retention/destruction-proposals/{id}` | One proposal. |
| POST | `/api/v1/retention/destruction-proposals/{id}/approve` | `{reason}`: destroys; 403 `four_eyes` for the proposer, 409 decided. |
| POST | `/api/v1/retention/destruction-proposals/{id}/reject` | `{reason}`; 403 `four_eyes`, 409 decided. |
| POST | `/api/v1/retention/storage-cleanup` | `{dryRun?}` (default true) → report. |
| GET | `/api/v1/retention/storage-cleanup` | The latest 20 runs. |

A document whose versions are all destroyed (or discarded) is left out of `GET /api/v1/documents` and answers 404; evidence reports show a destroyed version's destruction and check it against the destruction record (`destruction record`, `destroyed rendition`) instead of re-reading the rendition.

Tests: `DestructionServiceSpec` (PostgreSQL and SeaweedFS: destruction list, four eyes in service and database, tombstone, legal hold at proposal and approval, rejection, database guards, object removal with Object Lock retention, compaction rules and guard, discarded drafts, orphan clean-up with dry run, grace, holds and locks), `EvidenceReportApiSpec` (destruction through the API, 404 and list, intact evidence report), `SearchApiSpec` (a destroyed version leaves the index), `DocumentVersionSchemaSpec` (V35 transitions equal the lifecycle).
