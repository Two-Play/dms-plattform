# Frontend

Web UI of the DMS platform: Vite, React 19 and TypeScript (strict), Tailwind CSS 4 with shadcn/ui (ADR 0015), TanStack Router and TanStack Query, sign-in via OIDC (authorization code flow with PKCE) against ZITADEL, API client generated from the backend's OpenAPI document.

## Setup

Requires Node 24 and npm. `scripts/dev-setup.sh` in the repository root sets up everything (services, ZITADEL, demo users and data), writes `.env.local` and starts the dev server; see the main README. By hand: ZITADEL must be running (`docker compose up -d`) and set up (`scripts/zitadel-setup.sh`).

```bash
cd frontend
npm ci
cp .env.example .env.local   # fill in client and project id from ../.local/zitadel/dms.env
npm run dev                  # http://localhost:5173
```

Start the backend (`sbt app/run` in the repository root) for the dashboard and all other pages; tenant administrators see its health check under Admin › System status.

## Environment variables

Read by Vite from `.env.local` (not committed) or the environment. `VITE_*` values end up in the browser bundle, so never put secrets there.

| Variable               | Default                 | Meaning                                                                                                                                                                                |
| ---------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VITE_OIDC_ISSUER`     | `http://localhost:8085` | ZITADEL issuer (OIDC authority)                                                                                                                                                        |
| `VITE_OIDC_CLIENT_ID`  | required                | OIDC client id (`DMS_ZITADEL_CLIENT_ID`)                                                                                                                                               |
| `VITE_OIDC_PROJECT_ID` | none                    | ZITADEL project id (`DMS_ZITADEL_PROJECT_ID`); requests scope `urn:zitadel:iam:org:project:id:<id>:aud` so the access token audience contains the project, which the backend validates |
| `VITE_API_BASE_URL`    | empty (same origin)     | Base URL of the DMS API                                                                                                                                                                |
| `DMS_BACKEND_URL`      | `http://localhost:8080` | Dev server only: where the `/api` proxy forwards to                                                                                                                                    |

Redirect URI is `<origin>/callback`, post-logout URI `<origin>/`; both are registered by `scripts/zitadel-setup.sh` for `http://localhost:5173`. Requested scopes: `openid profile email offline_access`, `urn:zitadel:iam:user:resourceowner` (organization id claim, which the backend maps to the tenant), `urn:zitadel:iam:org:project:roles` (project roles claim) and the project audience scope. Tokens are kept in `sessionStorage` and renewed silently with the refresh token.

## API client

`src/api/schema.d.ts` is generated by `openapi-typescript` from `http://localhost:8080/docs/docs.yaml` (served by Tapir's Swagger bundle) and committed, so builds and CI need no running backend. Regenerate after API changes:

```bash
npm run api:generate
# backend on another port:
DMS_OPENAPI_URL=http://localhost:8091/docs/docs.yaml npm run api:generate
```

`src/api/client.ts` wraps it with `openapi-fetch` and adds `Authorization: Bearer <access token>` to every request. Vote requests (`POST /api/v1/workflow/tasks/{taskId}/votes`) additionally carry the OIDC ID token in `X-DMS-Id-Token`: approval votes need a recent sign-in (step-up), and ZITADEL puts `auth_time` only into the ID token (ADR 0024, addendum DMS-86). When a vote fails with `401 reauthentication_required` (`isReauthenticationRequired` in `src/auth/step-up.ts`), `reauthenticate(auth.signinRedirect)` signs in again with `prompt=login` and `max_age=0` and returns to the current page. The vote is not replayed automatically: the vote dialog remembers it (task, decision, reason) in `sessionStorage` (`src/auth/pending-vote.ts`, dropped after 30 minutes), and the inbox and the document page offer "Repeat vote", which opens the dialog prefilled; the user confirms it. `castVote` in `src/api/workflow.ts` is the client helper for the vote UI (DMS-91). Components get the client from `useApiClient()`, which makes it easy to replace in tests.

## Dev proxy

The app calls the API on its own origin with the backend's paths unchanged (`/health`, `/api/v1/...`); the Vite dev server forwards `/api` and `/health` to `DMS_BACKEND_URL`. The browser therefore only talks to its own origin, and the backend needs no CORS configuration. In production a reverse proxy (or the backend itself) is expected to serve the UI and the API under one origin; otherwise set `VITE_API_BASE_URL` to the API URL and add CORS to the backend.

## Routing

TanStack Router with **file-based routing**: the Vite plugin generates `src/routeTree.gen.ts` from `src/routes/` (committed so `tsc` works before the first build; do not edit by hand). File-based routing gives automatic code splitting per route and fully typed links without maintaining a route tree manually.

| Route                                               | File                                             | Access                                                                                                                                   |
| --------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `/sign-in`                                          | `routes/sign-in.tsx`                             | public landing and sign-in page                                                                                                          |
| `/callback`                                         | `routes/callback.tsx`                            | OIDC redirect target                                                                                                                     |
| `/`, `/documents`, `/templates`, `/tasks`, `/admin` | `routes/_app/*`                                  | signed in; `_app.tsx` is the pathless protected layout (app shell)                                                                       |

| `/documents/$documentId?version=…`                  | `routes/_app/documents/$documentId.tsx`          | signed in; a document: continue and submit a draft, workflow state (DMS-90); content, metadata and PDF of any readable version (DMS-112) |
| `/documents/$documentId/compare?from=…&to=…`        | `routes/_app/documents/$documentId_.compare.tsx` | signed in; comparison of two versions (DMS-54)                                                                                           |
| `/tasks`                                            | `routes/_app/tasks.tsx`                          | signed in; task inbox with votes and read confirmations (DMS-48)                                                                         |

| `/templates`                                        | `routes/_app/templates/index.tsx`                | signed in; templates for template designers (DMS-98)                                                                                     |

The protected layout checks `context.auth.isAuthenticated` in `beforeLoad` and redirects to `/sign-in?redirect=<path>`. After sign-in the original path is carried through the OIDC `state` and restored on `/callback` (only same-origin paths are accepted).

Colors, radius and fonts are CSS variables in `src/index.css` (`:root` for light, `.dark` for dark mode), mapped to Tailwind utilities through `@theme`. The theme toggle in the header sets the `dark` class on `<html>` and remembers the choice in `localStorage`; without a choice the system preference applies.

## New document and live preview (DMS-39)

`/documents/new` (`components/documents/`) lets an author pick a released template from the catalog (`GET /api/v1/templates`), fill in a form generated from the version's fields (`GET /api/v1/templates/{id}/versions/{version}/fields`) and watch the result next to the form:

- `field-values.ts` converts form input into `MetadataValue`s and validates it like the backend's field rules (type, min/max, decimal places, length, pattern, options, currencies). Inputs by type: text, number, amount with currency, date, selection, yes/no; multiple values as one per line, multiple selections as checkboxes. Required fields (needed for approval) carry a `*` and `aria-required`; messages appear inline and invalid values are not sent.
- The preview (`POST /api/v1/templates/{id}/versions/{version}/preview`) is a TanStack query keyed by the values, requested 300 ms after the last change (`useDebouncedValue`) and keeping the previous result while the next one loads. It shows the backend's HTML with the "Draft – not valid" banner and watermark, lists missing required values and focuses the field when a missing value (in the document or in the list) is clicked. Backend issues for a field are shown at the field while it still has the value that was sent.
- The HTML is produced by the backend renderer, which escapes all text, and inserted as is. It is styled by the **document stylesheet shared with the PDF rendering**: `modules/templates/core/src/main/resources/dms/templates/document.css`, imported through the alias `@dms-document` (`vite.config.ts`, `tsconfig*.json`; the dev server is allowed to read that directory). Do not copy it; see `modules/templates/README.md` for the class names.
- "Save draft" creates the document on the first save (`POST /api/v1/documents`) and saves further working states with `PUT /api/v1/documents/{id}/draft`. A title is required.

## Partner master (DMS-43)

For templates with reference fields (`references` in the fields response), the page shows a "From the partner master" group with one `PartnerPicker` per reference field (`components/documents/partner-picker.tsx`, `api/partners.ts`):

- Search by name or partner number (`GET /api/v1/partners`, 300 ms after the last keystroke, from 2 characters); a hit is taken over, can be changed or removed.
- The fields the reference fills are read-only, marked "From partner master – taken over from the system, not editable", and show the picked partner's values; the preview uses them.
- On save, these values are not sent as entered values; after the draft is saved, the picked partner is taken over on the server (`PUT /api/v1/documents/{id}/references/{key}`, `DELETE` when removed) as system values.
- If the partner master is unreachable (503/502), the backend's message is shown as an alert ("… You can save the draft without it and pick the partner later."); saving still works, and a failed take-over after saving is shown as a warning next to "Draft saved".

## Document list and drafts (DMS-90)

- `/documents` (`document-list-page.tsx`) lists the most recently changed documents the user may read (`GET /api/v1/documents`): "My drafts" (`mine` and status Draft) and "Other documents", each with status and version, linking to the document page.
- `/documents/$documentId` (`document-page.tsx`) loads the document (`GET /api/v1/documents/{id}`). A draft opens in the same workspace as "New document" (`document-workspace.tsx`: generated form, partner pickers, debounced preview, save); `draft-values.ts` turns the saved entered values back into form input and rebuilds the taken-over partner from the values it filled. Platform, computed and partner master values are not sent again; an unchanged partner is not taken over again. Other statuses show the version's content and metadata read-only (see below).
- "Submit for review" (both pages) saves the draft, then `POST /api/v1/documents/{id}/submit` starts the workflow; "New document" then opens the document page. The "Review and approval" card shows the cases from `GET /api/v1/documents/{id}/workflow` (status, round, current step, tasks with their assignees, votes).
- Errors: issues of a 422 (`invalid_values`, `not_editable`, `incomplete`) are shown at their fields while the field keeps the rejected value; `incomplete` at submission also lists the missing values (click focuses the field); a 409 tells the user to reload; `invalid` at submission (e.g. a changed locked section without an authorized deviation request) is shown with a generic hint.

## Document view, metadata and PDF (DMS-112, ADR 0039)

- The document page shows the content of the version it displays (`version-content.tsx`): `GET /api/v1/documents/{id}/versions/{versionId}/html` returns the backend's HTML fragment, rendered from the saved values with the "Draft – not valid" marking for versions that were never approved, and from the frozen version package for approved ones. It is shown in a scrollable, focusable box styled by the shared document stylesheet (`@dms-document`), like the live preview. A draft the caller edits keeps the workspace with its live preview.
- The metadata panel (`version-metadata.tsx`) lists status, version and revision index ("Index 1.1" = version number major.minor; open versions add their working state), document number (`documentNumber`, DMS-113, when present), author, owner, issuing body (the core field `organizationalUnit`, labelled "Herausgebende Stelle"), document class, valid from/until, confidentiality, approval (approver and date from the workflow approval, "on behalf of" for deputies), publication and template; then the other template fields under "Further details". Persons via `UserName`.
- "Download PDF" (`pdf-download.tsx`, `api/version-view.ts`): open versions get the draft PDF generated on demand (`…/draft.pdf`, marked on every page, not archived); approved versions the archived PDF/A (`…/rendition`). "Attach change history" adds the history of all versions up to this one: for drafts in the draft PDF, for approved versions as a copy generated on demand (`…/copy.pdf`) while the archived file stays unchanged. The files are fetched with the access token and handed over as blob.
- The version history offers "Show" per version; `?version=<id>` shows that version on the document page with a note and a link back to the current version.

## Task inbox and votes (DMS-48, DMS-91)

- `/tasks` (`components/tasks/task-inbox-page.tsx`) lists everything waiting for the user in one list: open review and approval tasks (`GET /api/v1/workflow/tasks`) and open read confirmations (`GET /api/v1/acknowledgements?status=open`, DMS-47). Workflow tasks carry only ids, so the inbox loads each document (`GET /api/v1/documents/{id}`, shared cache with the document page) for title, class path and version. Assignees are shown by name (`UserName`, DMS-110).
- Order (`inbox-items.ts`): overdue tasks first, then tasks with a deadline (earliest first), then tasks without one (oldest first). A task shows its deadline if it has one (`dueAt`; workflow deadlines follow with DMS-87), otherwise since when it is open; overdue tasks get a red border, an "Overdue" badge and "Overdue since …". The kind `ReviewDate` (periodic review) is typed but has no source yet.
- Actions in the list: "Vote…" opens the vote dialog (`vote-dialog.tsx`); a read confirmation offers "Open document" (`POST …/versions/{versionId}/opened`, then the document page) and, once opened, "Confirm read" (`POST …/versions/{versionId}/acknowledgement`). If the backend has no acknowledgement endpoint yet (404), read confirmations are left out without an error. The types in `api/acknowledgements.ts` come from the generated schema.
- The document page of a published version that requires acknowledgement (`components/documents/acknowledgement-panel.tsx`, DMS-47) records the opening when it is displayed (`POST …/opened`), reads the caller's state (`GET …/versions/{versionId}/acknowledgement`) and offers "Acknowledge" once the opening is recorded; afterwards it shows the acknowledgement with version and time.
- Vote dialog: decisions Approve, Approve with conditions and Request changes (review steps) or Reject (approval steps); a reason is required for everything except a plain approval (checked before sending; the backend answers 422 too). On `401 reauthentication_required` the dialog explains why, remembers the vote and offers "Sign in again" (see API client above). After a vote the task list, the document and its workflow are reloaded.
- The document page's "Review and approval" card shows the caller's open tasks on the document with the same "Vote…" button.
- Navigation by role (`GET /api/v1/me`, `useMe` in `api/me.ts`): Home, Documents, Library, Search and Tasks for everyone, Templates for template designers, Compliance for compliance officers, Legal holds and Retention for records managers whose assignment covers the whole tenant (`canManageLegalHolds` in `api/legal-holds.ts`, `canManageRetention` in `api/retention.ts`, the rule of these endpoints), Admin for tenant administrators. The user menu links to "Deputies". Hiding entries is a convenience; the API enforces the permissions.

## Compliance cockpit (DMS-59, ADR 0036)

- `/compliance` (`components/compliance/compliance-page.tsx`) shows three key figure cards (overdue reviews, acknowledgement rate, open acknowledgements) and tables of overdue reviews per unit and per owner and of acknowledgement rates per unit (`GET /api/v1/compliance/overview`). Every figure is a link to its list below, kept in the URL (`view=reviews|acknowledgements`, `unit`, `owner`, `document`; parsed in `compliance-params.ts`); an empty `unit` or `owner` selects versions without one ("No unit", "No owner").
- The acknowledgement list shows figures only. "Who has not acknowledged" opens a dialog that requires a purpose (escalation or reminder) and a reason before it requests the names (`GET …/acknowledgements/{documentId}/{versionId}/open`); the backend records purpose and reason in the audit trail. The names are not cached.

## Legal holds (DMS-106, ADR 0031, 0047)

- `/legal-holds` (`components/legal-holds/legal-holds-page.tsx`) lists active, released or all holds (`status`) and opens one (`hold`): matter, reason, who set and released it, and its documents with who added or removed them, how, when and why (titles only of documents the records manager may manage). While active: "Add documents" (from a search the records manager checks, or pasted document links or ids), "Remove" per document (reason) and "Release" (reason and an explicit confirmation). New holds need a name and a reason.
- Search results are confirmed exactly: "Check search" (and "Put under legal hold" on the search page, `search-hold-dialog.tsx`) asks the backend for the documents of the whole result (`POST /api/v1/legal-holds/search-preview`); confirming sends the hit count and the preview's fingerprint, so the backend refuses with `409 result_changed` if the search finds other documents by then, and the dialog asks to check again.
- `LegalHoldBadge` (`legal-hold-badge.tsx`) marks held documents on the document page, in the document list, the search hits and the library (`legalHold`). Only callers the backend sends `legalHolds` to (records managers of the document) can open it to see the names of the holds with links; nobody else ever receives a hold name.

## Retention and destruction (DMS-82, ADR 0054)

- `/retention` (`components/retention/retention-page.tsx`, API in `api/retention.ts`) has four sections, kept in the URL (`tab`): **Destruction list** (`GET /api/v1/retention/destruction-list`): versions whose retention ended, with class, rule and text filters (`class`, `rule`, `q`, filtered in the browser), how many versions have no rule or a running retention, and a marker for legal holds and open proposals; versions under legal hold, in an open proposal or of documents the records manager may not manage cannot be selected. "Propose for destruction" asks for a reason and opens the proposals. **Proposals** (open, approved, rejected, all): reason, who proposed and decided, the versions with their outcome (destroyed with rendition, approved-content and file checksums, or not destroyed with the cause). The own open proposal only shows that a second records manager decides it (four eyes; `403 four_eyes` is explained too); others can "Approve and destroy" (reason and an explicit confirmation) or "Reject" (reason). **Retention rules**: key, name, period in months, trigger and "from year end", created and edited in a dialog (key checked like the backend). **Storage clean-up**: "Check (dry run)" and "Clean up" (with confirmation) of orphaned objects, the latest report with every object found and the latest runs.
- After a proposal or decision the destruction list, proposals, document lists, search and library are reloaded: destroyed versions leave them.

## Administration and deputies (DMS-105, DMS-99)

- `/admin` (`components/admin/admin-page.tsx`) is for tenant administrators (others see a hint; the API enforces it) and has the tabs access groups, number ranges, deputyships and system status. **Access groups** (`groups-panel.tsx`): create a group (key checked like the backend: lowercase letters, digits and hyphens), pick a group, rename it (`PUT /api/v1/groups/{key}`; the key stays), add a member picked by name (people picker, DMS-111) and remove current members. The member list keeps former members with who added and removed them when. The backend resolves the participants of open tasks of confidential documents naming the group again when members join or leave, so the inbox is reloaded after a change. **Deputyships**: all deputyships of the tenant (`GET /api/v1/deputyships?all=true`), setting one for anyone (principal field) and ending running or scheduled ones.
- **Number ranges** (DMS-113, `number-ranges-panel.tsx`, API in `api/number-ranges.ts`): create a range (key, name, pattern such as `VTR-{YYYY}-{NNNN}`, start value, yearly reset) with a live preview of the next number (`POST /api/v1/admin/number-ranges/preview`, debounced; the backend's problems are shown), list the ranges with their next number and classes, edit a range (only future numbers change), and assign per document class: inherit from the parent, no number range, or a range; the effective range shows where it is inherited from. Classes with a range offer "Number existing documents" (DMS-116, `number-backfill-dialog.tsx`): the dialog shows how many documents have no number (`GET …/{classId}/backfill`) and runs the backfill on confirmation (`POST`), then summarizes numbered, skipped (with reasons), failed and remaining documents.
- The document list and the search hits show the document number (`documentNumber`, DMS-116) when a document has one.
- Document page (`documents/document-number-action.tsx`): the document number in the header actions and, when the backend allows it (`canAssignNumber`: records managers and the document's owner while the number is not frozen), "Assign number" / "Change number" opens a dialog with number and required reason (`POST /api/v1/documents/{id}/number`); conflicts such as a taken number are shown in the dialog.
- `/deputies` (`components/deputies/my-deputies-page.tsx`, user menu → "Deputies") is for everyone: set a deputy (`deputyship-form.tsx`: deputy, optional start, end, roles, document class, reason; checked before sending, the backend's reason shown otherwise), "My deputies" and "I stand in for" (`deputyship-table.tsx`) with "End now".
- The task inbox marks tasks forwarded by an active deputyship with "On behalf of …" (`actingFor`).
- Users are shown by name (`UserName`, DMS-110); group members, principal and deputy are picked by name with the people picker (DMS-111).

## Search and "valid on" (DMS-52, DMS-53)

- `/search` (`components/search/search-page.tsx`) keeps its state in the URL (`q`, `class`, `status`, `lang`, `page`, `validOn`; parsed in `search-params.ts`), so searches can be bookmarked. Search text and the facets class, status and language call `GET /api/v1/search` (20 hits per page, Previous/Next). The endpoint (DMS-51/52, ADR 0029) is typed by the generated schema; only versions the caller may read are counted and returned, and a 404 (backend without search) shows "Search is not available yet" instead of an error.
- Snippets contain `<mark>…</mark>` highlights. `snippetParts` (`components/search/snippet.ts`) splits them at these tags and everything is rendered as React text; any other markup in a snippet stays visible text and is never interpreted (no `dangerouslySetInnerHTML`).
- A "Valid on" date switches to `GET /api/v1/documents/valid-at?date=…&class=…`: per document and validity scope the version in force at the end of that day (tenant time zone), with status now, validity period and approver (and the approver a deputy acted for). The class facet is computed from the listed versions; the search text is not applied. "Export CSV" fetches `…/valid-at/export.csv` with the access token and hands the file to the browser as a blob (the name comes from `Content-Disposition`).

## Library (DMS-119, ADR 0043)

- `/library` (`components/library/library-page.tsx`, navigation "Library" / "Bibliothek" for everyone) lists the documents valid today that the user may read (`GET /api/v1/library`, `api/library.ts`): as cards (class, title, document number, index, issuing body, description from the field `summary`, valid from, scope, tags) or as a list (`DataTable`); the title opens the document page.
- Badges: "New" (first published on or after the reference date), "Changed since …" (a later version became valid since then), "Acknowledgement open" (the user has yet to acknowledge the version; the document page records opening and confirmation) and "Review due".
- Filters: free text (sent 300 ms after typing stops), the facets class, issuing body, tags and confidentiality (several values per facet; counts from the backend, each facet ignoring its own filter), "New or changed since {date}" and "Awaiting my acknowledgement"; sorting by title, document number, valid from or last change with order; the reference date of the markers (default 30 days ago). Everything is kept in the URL (`library-params.ts`: lists comma-separated, e.g. `?class=policy,instruction&unit=HR&changed=true`), so views can be shared. 24 documents per page.

## Attachments (DMS-114, ADR 0041)

- The document page shows the "Attachments" card (`components/documents/attachments-panel.tsx`, `api/attachments.ts`) for the shown version: `GET /api/v1/documents/{id}/versions/{versionId}/attachments` lists name, size, type icon, who added it when and the SHA-256; "Download" fetches `GET …/attachments/{attachmentId}` with the access token and hands the file to the browser as a blob.
- While the version is a draft and the backend says the caller may edit it (`editable`), files are added by drag and drop onto the drop zone or with "Choose files…" (a real button that opens the hidden file input, so it works with the keyboard). Files are sent one after the other as `multipart/form-data` with `XMLHttpRequest`, which reports the upload progress (`<progress>` per file, announced politely); the file part is sent as `application/octet-stream` and the backend takes the media type from the name. Empty files, files above the limit the backend reports (`maxSizeBytes`) and blocked types (programs and scripts, the backend's default list) are refused before sending; the backend checks again and its refusals (too large, blocked, infected, scanner unavailable, name taken) are shown at the file.
- Rename and remove open dialogs (`PATCH`/`DELETE …/attachments/{attachmentId}`); removing only takes the file out of the draft. After submission the list is read-only.
- `AttachmentsPanel` takes the upload function as optional prop (`upload`), so tests replace the network upload.
- "Download PDF" offers "Attach list of attachments" next to the change history (`attachments=true` on `draft.pdf`/`copy.pdf`, DMS-115).

## File documents and Word templates (DMS-115, ADR 0042)

- "New document" (`new-document-page.tsx`) lists Word templates from `GET /api/v1/word-templates` as "<name> (Word)"; a structured template can also be used for a file document ("Upload a file after saving"). The workspace (`document-workspace.tsx`, prop `kind`) creates them with `POST /api/v1/documents/word` or `POST /api/v1/documents` with `kind: File`, shows a hint instead of the live preview and continues on the document page (`onCreated`).
- On the document page a file document (`DocumentView.kind === 'File'`) shows `FileContentPanel` (`file-content-panel.tsx`, `api/word.ts`) instead of the rendered content: the original with "Download original" and, for DOCX, "Download Word (filled)"; "Upload file…/Replace file…" in a draft (`PUT /api/v1/documents/{id}/file`, multipart with progress, convertible types only); the fields of the Word document (`GET …/word-fields`: automatic ones read-only with the value the platform fills, manual ones as inputs saved with `PUT /api/v1/documents/{id}/word-fields`); "Show preview" loads `GET …/preview.pdf` into an iframe (a conversion takes seconds, so it is loaded on request). The metadata form stays as for structured drafts.
- Templates (`template-list-page.tsx`) marks Word templates with a "Word" badge (`GET /api/v1/admin/word-templates`) and offers "New Word template" (`NewWordTemplateCard`): name, the document class from the read-only class list for designers (`GET /api/v1/admin/template-classes`, DMS-121), the DOCX; it creates the template with empty content and uploads the file. The template page shows `WordTemplatePanel` for Word templates instead of the content editor and test mode: download, replace (draft), the field definitions table (label, type, required, automatic/manual) and "New version" through `POST …/word-versions`.
- DMS-121 (ADR 0044): `PdfDownload` offers "Download as Word" for structured documents (`wordExport`, `GET …/document.docx` with the same options as the PDF); the version comparison shows the originals of file versions (`original`: names, sizes, SHA-256, whether the Word text was compared), names the Word text section and translates the version property labels (`docs.compare.properties`).
- `WordFieldHelp` explains the field conventions (content controls with tag `dms:<key>` for automatic and any other tag for manual fields, `{{key}}` placeholders) on the document and template pages.
- DMS-122 (ADR 0046): field types follow the content controls of the Word file. `WordFieldInput` (`word-field-input.tsx`) renders the input of a manual field by type: text, date, number, a check box (`Checkbox`, values `true`/`false`, from `w14:checkbox`), a select of the field's options (`Choice`, from drop-down lists and combo boxes or options a designer defined), or a table of rows (`Rows`, a repeating section: one input per column, "Add row", "Remove row n"; required columns are marked and checked on submission, not when saving). A Rows value is a JSON array of objects by column key (`parseRows`/`serializeRows` in `api/word.ts`); the backend stores it canonically (trimmed, empty rows dropped). Read-only, `WordFieldValue` shows check boxes as yes/no, dates in the UI language and rows as a table. Warnings of the field scan (e.g. nested repeating sections) are shown at the field and on the template page. The template page lets designers edit the options of Choice fields (one per line) and the label, type and required flag of the columns of Rows fields; Rows cannot be chosen for other fields. Excel (`.xlsx`) and PowerPoint (`.pptx`) originals have fields too (`{{key}}` placeholders); "Download filled file" uses `GET …/versions/{versionId}/filled` for all three formats (`isFillableFile`). The help (`WordFieldHelp`) explains typed controls, repeating sections, split placeholders and Excel/PowerPoint.

## Version history and comparison (DMS-54)

- The document page lists the versions the caller may read (`GET /api/v1/documents/{id}/versions`) newest first with status, change kind and the author's change summary. Two picked versions ("Compare selected versions", the older one becomes `from`) or "Changes since …" on a version open `/documents/$documentId/compare?from=…&to=…` (`components/documents/version-compare-page.tsx`).
- The comparison (`GET /api/v1/documents/{id}/compare`, ADR 0033) shows the change summaries on top, then tabs for text, field values and metadata. Text changes are marked with `<ins>`/`<del>` (with screen reader labels); "Show unchanged text" adds the unchanged sections and blocks. All content is rendered as React text, never as HTML. A 403 (one of the versions is not readable) is explained on the page.

## Template management (DMS-98)

For template designers (`EditTemplates`; the API answers 403 to everyone else):

- `/templates` (`components/templates/template-list-page.tsx`) lists the latest version of every template (`GET /api/v1/admin/templates`) with version number, status and creator.
- `/templates/$templateId` (`template-page.tsx`) loads all versions (`GET /api/v1/admin/templates/{id}`); `?version=n` picks one, otherwise the latest is shown. Per version: status and history (created, changed by, released by and when, from the version itself; the audit trail of status changes is not exposed by the API yet), the fields of the class profile (`GET …/versions/{version}/fields`, designer endpoint for any status), the content and the test mode.
- Content: a draft is edited as JSON (`content-editor.tsx`); "Check" calls `POST /api/v1/admin/templates/check`, "Save draft" `PUT …/versions/{version}`. Invalid JSON is reported before anything is sent. A 422 `invalid_content` on save carries the compiler issues only as one text, so the editor runs the check afterwards and lists the issues with their location (section › block path › part, line, column). Other versions show the content read-only; "New version" creates the next draft from the latest version when no version is open. A structured editor follows later.
- Test mode (`test-mode-panel.tsx`, `POST …/versions/{version}/test` with generated sample data in English or German): branch coverage per condition, the generated cases, and each case rendered as HTML by the backend (`html`, same renderer and document stylesheet as the live preview, draft marking).
- Status (`template-lifecycle.ts` mirrors `TemplateLifecycle`): Draft → "Start testing"; Testing → "Back to draft" or "Release…"; Released → "Deprecate…" (confirmation); Deprecated → "Archive". "Release…" opens `release-dialog.tsx`, which loads the impact analysis (`GET /api/v1/templates/{id}/versions/{version}/impact`): documents on earlier versions per status, open drafts with title, author, status and last change, and the backend's explanation that a release changes no existing document. Titles of confidential drafts the caller may not read arrive masked (`titleMasked`) and are shown with a lock. If the signed-in user created or changed the version, the page explains that another designer has to release it (four-eyes principle); the backend decides, and its 403 `segregation_of_duties` is shown in the dialog. A 409 (concurrent change, open version) asks to reload.
- Users (creators, editors, releasers, draft authors) are shown by name (`UserName`, DMS-110).

## Dashboard, shell and page building blocks (DMS-109)

- **Home** (`components/home/home-page.tsx`) is a personal dashboard: greeting, quick actions (New document, Search) and cards with count, the top five items and a "view all" link: open tasks (`GET /api/v1/workflow/tasks` and periodic reviews `GET /api/v1/reviews?status=open`), read confirmations, own drafts and recently published documents (both from the document list). Role cards only when the role applies: templates in testing (template designers), overdue reviews and read confirmation rate with a link to the cockpit (compliance officers), system status (tenant administrators; also a tab on the admin page). Every card has a loading skeleton, an empty state with the next step and an error with "Try again" (`dashboard-card.tsx`).
- **Shell** (`components/app-shell.tsx`): skip link to the content; sticky header with a global search field (submits to `/search?q=`, hidden on the search page itself); desktop sidebar that stays in view on long pages and highlights the section of nested pages (`/documents/...` → Documents); below `md` a menu button instead of the sidebar; open task count on "Tasks" (workflow tasks, periodic reviews and read confirmations; given to screen readers as description of the link). After navigating to another path, focus moves to the page heading (or `main`), so screen readers announce the new page. `scroll-padding-top` keeps focused elements clear of the sticky header.
- **Page building blocks** (`components/shared/`): `PageHeader` (title, description, actions, breadcrumbs; sets the tab title "Title · DMS"), `Breadcrumbs` on nested pages (Documents › Document › Compare, Templates › name), `ErrorState` (user-facing text by HTTP status or network error: 401, 403, 404, 409, 400/422, 5xx; the backend's own message as detail, generic "failed with HTTP n" fallbacks are hidden; "Try again" calls `refetch` where retrying can help), `InlineError` for failed actions, `EmptyState`, `LoadingState` (skeleton rows with a screen-reader text) and `DataTable` (documents and templates lists). Error texts live in `error-messages.ts`.
- **Toasts** (`lib/toast.ts`, `shared/toaster.tsx`): a small own implementation instead of a dependency; a polite live region, at most three at a time, dismissable, paused while hovered or focused. Shown after saving and submitting drafts, votes, read confirmations, periodic review decisions, template status changes, group and member changes and deputyships. Confirmation dialogs for destructive actions stay.
- **Sign-in name**: ZITADEL puts name and email claims into the ID token only with "user info inside ID token"; the client therefore loads the userinfo endpoint (`loadUserInfo`), and `scripts/zitadel-setup.sh` enables the assertion for new setups. The shell shows name, given and family name, user name or email, in this order (`auth/profile.ts`).
- **Visual consistency**: read-only inputs (values taken over from the partner master) have a dashed border, muted background and a lock; disabled primary buttons are neutral grey instead of faded blue; task inbox entries share one layout (badges, title, context, date; actions on the right). All UI texts live in the message catalogs (see Localization below).

## Localization (DMS-110, ADR 0038)

The UI speaks German (default) and English. Texts live in message catalogs, one file per area and language: `src/i18n/locales/en/*.ts` (source) and `src/i18n/locales/de/*.ts`; `pages.ts` and `base.ts` list the namespaces.

- **Library choice**: a small own module (`src/i18n/core.ts`, `src/i18n/index.ts`) instead of react-i18next: no dependency (~2 kB instead of ~40 kB), and fully typed. `t('tasks.voteRecorded', { decision, title })` is checked by the compiler: the key must exist, and the parameters are inferred from the `{placeholders}` of the English text. The German catalog has the type `Translation<typeof en…>`, so a missing or extra key fails `tsc`. A unit test (`src/i18n/i18n.test.ts`) checks that every German text has the same placeholders. Plurals: `plural({ zero?, one, other })` in the catalog, picked with `Intl.PluralRules` from the `count` parameter. Runtime keys (statuses, roles and decisions the API sends) use `tOptional(...)`, which returns `undefined` for unknown values; `statusLabel` and `roleLabel` fall back to the raw value.
- **Language**: default is the stored choice, else the browser's preferred language if it is German or English, else German. The user menu has a language switch; the choice is stored in `localStorage` (`dms-locale`) and per signed-in user (`dms-locale:<sub>`), and `<html lang>` follows it. `App` keys the router by the language, so a switch renders every page again (data stays cached; unsaved form input is lost). Therefore `t` is a plain function usable in components, helpers and toasts; never build texts at module load time (column definitions are functions for that reason).
- **Formats**: `src/i18n/format.ts` (`formatDate`, `formatDateTime`, `formatPlainDate` for `YYYY-MM-DD`, `formatLongDate`, `formatNumber`, `formatPercent`) use `Intl` with `de-DE` or `en-GB`. Do not use `Intl.*Format(undefined, …)` or `toLocale*()` without the active locale.
- **Tone**: German texts use neutral, impersonal forms where possible ("Entwurf speichern", "Bitte einen Titel eingeben", "Keine Berechtigung") and "Sie" where a direct address cannot be avoided ("Ihre Aufgabe"); never "du". Terms follow the business concept (`docs/fachkonzept.html`): Dokument, Vorlage, Entwurf, In Prüfung, In Freigabe, Freigegeben, Veröffentlicht, Kenntnisnahme, Rezertifizierung, Stellvertretung, Außer Kraft setzen, Abweichung, Vier-Augen-Prinzip, Prüfer/in, Genehmiger/in, Verantwortliche/r (owner), Aufgabeneingang.
- **Backend messages** (`ApiError.message`) are English; the UI shows its own text and the backend's message as detail.
- **Tests** run in English: `src/test/setup.ts` calls `setLocale('en')` before each test. German smoke tests (`src/components/german-smoke.test.tsx`) call `setLocale('de')` and check the shell, the task inbox, date formats and the language switch.
- **Adding a text**: add the key to the English file, then to the German one (the build fails otherwise), and call `t('namespace.key', params)`.

## User names (DMS-110, ADR 0037)

The API identifies people by user id; `GET /api/v1/users?ids=…` resolves ids of the caller's tenant to display names through the backend's user directory (ZITADEL). `UserName` (`components/shared/user-name.tsx`) shows the name with the id as tooltip (`title`) and falls back to the id while loading, for unknown ids and when the directory is unavailable; `UserNames` lists several. `useUser` (`api/users.ts`) collects the ids asked for during one tick and resolves them with one request (`UserLoader`, DataLoader style), cached for ten minutes; `useUserLabel` gives the name for aria labels and `cachedUserName` for toasts. Names are shown in the task inbox and workflow panel (assignees, voters, approver, "on behalf of"), the document page (author, owner, person fields of the metadata), the version history (author), the "valid on" list (approver, deputy), the compliance cockpit (owners, readers without acknowledgement), the administration (group members, who added or removed them, deputyships), the templates (creator, editors, releaser, draft authors in the impact analysis) and the evidence report panel (creator). The evidence report PDF/JSON, the audit trail and CSV exports keep user ids: they are legal records and need the stable identifier.

### People picker (DMS-111)

Wherever a person is entered, it is picked by name: `PersonPicker` (`components/shared/person-picker.tsx`, "Select a person" / "Person auswählen") searches `GET /api/v1/users/search?q=…&limit=10` (`personSearchQuery` in `api/users.ts`, 250 ms after the last keystroke, from two characters, cached for a minute) and stores the user id; hits show name and email, the picked person shows name and email until the text is changed or "Clear selection" is pressed. It is a WAI-ARIA combobox with a list box: arrow keys (and Home/End) move through the hits (`aria-activedescendant`), Enter picks without submitting the form, Escape closes the list and then clears the text; hints, "Searching…", the number of hits, "Nobody found" and errors are announced in a live region (`role="status"`). If the backend answers `user_directory_unavailable` (ZITADEL down or no directory configured), the typed text can be taken as user id, as before. `PeoplePicker` takes several people (list with a remove button each). Used for group members, principal and deputy of deputyships, and person fields (`PersonRef`, e.g. the owner) of the document form, single and multiple. Picked people go into the name cache, so `UserName` and toasts show them without another request.
